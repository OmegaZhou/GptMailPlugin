# 当前开发目标与验收要求

本文件按用户 2026-10-11 最新反馈修正：首次连接时填写服务器地址并登录服务器账号；认证后不再要求填写地址或服务器密钥。替代单邮箱 OAuth 和管理密钥二次登录的交互目标。

1. 保留原仓库、原插件身份和托管服务；由 nginx 管理 `/mail-mcp`，不依赖本机进程，不增加服务端 `/panel`。
2. 从插件内直接打开常驻邮箱管理面板，用户不需要聊天指令、寻找另一浏览器窗口或手动访问授权地址。
3. 在同一面板添加、编辑、测试、移除多个邮箱及选择默认邮箱。OAuth 仅负责首次连接；新增邮箱不再重新授权，新增后当前连接的邮件工具立即可用。
4. 面板显示实际连接的服务地址、已登录的服务器账号、授权状态和连接测试结果。不再提供服务器 API 密钥输入或重复认证表单。
5. 服务器可配置，允许在首次连接认证流程中填写；认证成功后保存实际连接，后续工具必须使用该地址。主动更换服务器应重新进入连接流程，而不是修改仅供导出的 JSON。认证后不得要求再次填写服务器地址。
6. 地址、密钥及邮箱凭据不写入公开源码或报告；凭据不进入聊天模型。
   MCP 地址与 OAuth 连接凭证由插件或宿主维护，不能依赖目标邮件服务接口来确定自己应连接的地址。连接跨端持久化，重新打开或换设备自动恢复，无需反复填写地址、密码或密钥。登录前显示认证目标；更换地址时不能自动向新地址发送旧凭据。聊天和模型可见工具结果不输出连接地址或凭据。
   首次尚未配置地址、目标服务不可达或服务迁移后，插件配置入口仍必须可打开并允许修改连接。不得暗中增加固定中转服务作为配置来源来替代此要求。
7. 在用户实际使用的 ChatGPT 界面验证入口、配置保存、第二邮箱无需 OAuth、账户选择和读信。不得以测试通过、模拟邮箱或压缩包替代真实验收。
8. 每次插件更新都检查托管服务的接口、工具清单和 UI 资源是否需要同步适配；需要时同步部署并验证线上版本，不能只上传插件压缩包。
9. 认证系统作为独立 GptPluginOauth 仓库，以 `auth/` Git submodule 引入；Authelia 是认证仓库内部的依赖。多个插件可共享账号和认证服务，分别登记客户端、资源和权限。认证模块维护账号、邮件临时密码及 OAuth 授权，GptMail 只验证令牌和管理邮箱。真实 ChatGPT 授权及 MCP 工具调用已通过。

## 当前未完成

0.5.4 已补充服务器账号显示：私有配置将已验证 subject 映射到登录账号名称，经 `_meta` 返回面板。相关认证与面板测试通过，服务器和原插件已同步发布；刷新宿主工具后，真实 ChatGPT 页面显示的账号与管理员创建的登录账号一致，授权自动恢复。账号名称不进入模型可见的连接资料。

- 原插件 0.5.3 的“网站”链接已实际验证在同一浏览器标签直接打开内嵌邮箱面板，并自动恢复授权。顶部主按钮仍为“在聊天中试用”；关联邮箱应用的顶部按钮为“打开插件”。链接入口和主按钮必须如实区分。
- 首次创建连接已在宿主填写 MCP 地址，并完成账号登录及连接保存。页面重载、邮件服务重启后均自动恢复，无需再次填写地址或密钥。独立 Chrome 会话也已自动恢复相同连接，未重复登录；这验证跨浏览器持久化，但不等于第二台物理设备验收。主动更换服务器及第二设备尚未验收。
- 认证失败根因已修复：Authelia 使用 `scp` 数组，原校验器只读取 `scope` 字符串。真实 ChatGPT 的初始化、工具发现与面板工具调用已成功。原插件 0.5.2 已绑定有效应用并安装，服务同步部署。
- `settings_bootstrap` 只恢复面板临时会话，调用依赖宿主已经保存的 MCP 连接；服务端回传地址只供显示，不用于选择请求目标。
- 真实邮箱保存及读信尚待验收。已打开添加邮箱表单，请用户直接填写凭据；不在聊天收集密码，不以模拟邮箱替代。

不考虑旧方案兼容性：移除单邮箱 OAuth 表单和授权分支，统一采用服务连接。升级时使旧授权失效，首次重新连接时明确授权当前及后续添加的邮箱；日常新增邮箱不再触发 OAuth。
